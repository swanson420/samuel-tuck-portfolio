MERCYZERO

A live security-testing web app, built by directing AI and verified like a QA lead would.

Most security scanners give you a list of warnings and a shrug. MERCYZERO runs a seeded, repeatable test against a target. One component, and only one, decides pass or fail. Then it proves the result: it replays the run byte for byte, shrinks the failure to the smallest request that still breaks, fingerprints it, and seals everything into a content-hashed digest.

I built it mainly through conversational AI guided by Goggles & Lens, with AI agents handling a small share of the implementation. It has a mobile-friendly console, a Postgres database, and automatic deploys that only happen when every test passes.

  • 1,004 tests: 999 pass, 0 fail, 5 run in the database gate
  • Architecture is enforced in CI. Forbidden imports between modules fail the build.
  • Deploys only on green. Railway ships main only after the full gate passes.
  • Real-browser tests on every screen. A headless Chromium run drives the whole console.

SLAav

An SLA authority layer for Zendesk-style support teams.

When a support SLA is breached, someone pays, and the platform's own logs can be edited. SLAav records every SLA event in an append-only ledger that rejects changes, links each entry into an HMAC-SHA256 hash chain, sorts breaches into five root causes, and gives finance and operations a dollar figure they can defend. Today it's a proven backend: the finance and operations views are API endpoints, and the screens come next.

  • 193 tests run against a live Postgres in CI
  • Hash chain checked independently. A test recomputes every HMAC and requires an exact match.
  • 14 adversarial ingestion tests. Bad data goes to quarantine and is never quietly fixed up.
  • Every claim pinned to a commit and a CI run in its evidence package.

02 / Method

Goggles & Lens

My own two-layer prompting method. Instead of rewriting a giant prompt every time, I set two layers that stay on until I change them. It keeps the AI's output consistent and accountable from architecture through testing and review.

Layer 1

Goggles

Set the field: the expertise, methods, priorities, and standards the AI works to.

GOGGLES: security QA engineer
+
Layer 2

Lens

Set the perspective: how it reasons, what it focuses on, and what it puts first.

LENS: adversarial, assume it's broken
=
Result

Steered output

A focused reviewer that hunts for real defects, and stays that way until the layers change.

persists across the session

The loop I run on every project

01

Write the requirements

Clear, testable requirements first, so there's something to hold the output to.

02

Steer the build

Goggles & Lens set who the AI is and how it thinks. AI agents take a small, scoped share.

03

Evaluate against instructions

I check every result against what was asked, not against how confident the AI sounds.

04

Use it like a user

Click every screen on the live app and ask the questions that expose what's broken.

05

Require proof

Nothing ships unless every test passes. Unfinished items get listed openly.
